Manual repro: Kubestellar Fails to Orchestrate PersistentVolumeClaims with Late-Initialization Fields
=============================================================================

Self-contained bug submission bundle. All paths below are relative to this
folder:

  manual_tests/pvc_null_storageclass_repro/

Goal
----
Reproduce the bug that causes PVC to enter untracked state
  - WDS PVC created with storageClassName: null
  - BindingPolicy downsyncs desired PVC to edge via ManifestWork
  - Edge PVC is created with the cluster default storageClassName (standard)
  - WDS attempts to rollback from standard back to null
  - Klusterlet apply fails: Forbidden: spec is immutable after creation
  - ManifestWork status shows AppliedManifestWorkFailed with diff:
      - "StorageClassName": "standard",
      + "StorageClassName": null,

Apply the null manifest and policy on WDS; the failure appears on the
edge ManifestWork. After that failure, the hub stops tracking the PVC:
further updates on WDS do not reach the edge.


Files in this folder
--------------------

  setup_kubestellar.sh                   (provision Kind + KubeStellar v0.29.0)

What NOT to do
--------------
  - Run kubectl without KUBECONFIG=~/.kube/kubeflex (edge-* / wds1 contexts live there)
  - Apply manifests from the Ursa repo root (use this folder; paths are relative)
  - Apply fix-klusterlet-rbac.yaml on WDS instead of edges
  - Use clusteradm v1.x with KubeStellar 0.29 hub (token SA mismatch)



Expected behaviour
------------------
  1. Hub and edge agree on defaulted fields before downsync diverges.
     WDS is stripped of most admission/defaulting controllers that would
     set values such as storageClassName on a spoke. When the edge API
     server defaults a field (e.g. PVC storageClassName → standard), the
     hub should learn that effective value — for example via upsync or
     status feedback from the edge — so desired state on WDS matches what
     the edge actually created. Hub and edge should not fight over a field
     the hub never had a chance to default.

  2. Partial tracking after an apply failure (design preference).
     Even when one immutable field cannot be reconciled, it would be useful
     if the hub continued to track and downsync other fields on the same
     object (e.g. labels, annotations, mutable spec). Losing all tracking
     because of a single late-initialized field makes the object effectively
     unmanaged on that edge.
