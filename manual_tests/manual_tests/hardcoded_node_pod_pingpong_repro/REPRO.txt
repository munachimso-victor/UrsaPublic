Manual repro: hardcoded nodeName Pod → edge deletes → work-agent recreates (existence ping-pong)
===============================================================================================

Self-contained bug submission bundle. All paths below are relative to this folder:

  manual_tests/hardcoded_node_pod_pingpong_repro/


Goal
----
Reproduce a create/delete loop where:

  - Hub downsyncs a Pod with spec.nodeName set to a name that does NOT
    exist on the edge (your-specific-node-name)
  - Edge admits/applies the Pod (ManifestWork Applied=True)
  - Edge node lifecycle / orphan-pod cleanup deletes the Pod (node never
    existed)
  - Spoke work-agent sees the object missing vs ManifestWork desired state
    and recreates it
  - Edge deletes again → existence ping-pong (present ↔ absent)

Unlike Job selector / PVC volumeName (immutable field → Applied=False),
this often keeps Applied=True while Available=False (ResourcesNotAvailable),
and the failure mode is object flapping, not a stuck apply.

Ursa automated hit (same mechanism):
  tests/2026-07-26_shard0/run_ursa-bp-hardcoded-node-pod__pert__reset_always/
    hardcoded-node-pod/testcase_001_ursa-bp-hardcoded-node-pod_original.txt
  Observed: UNSTABLE(2) over 240s — Pod disappeared ~t=15s, reappeared ~t=205s
  MW: Applied=True, Available=False (ResourcesNotAvailable)


How the ping-pong works (step-by-step)
--------------------------------------
  1. Desired state on WDS
     Pod hardcoded-node-pod with
       spec.nodeName: your-specific-node-name
     (no such Node on Kind edge-1 / edge-2).
     ConfigMap sibling for a stable contrast object.

  2. BindingPolicy selects edge-1 / edge-2 and downsyncs
     Pod + ConfigMap.

  3. KubeStellar creates ManifestWorks on ITS (ns=edge-*).
     Work agent applies the Pod on the spoke.

  4. Edge Node lifecycle / orphan-pod cleanup treats the Pod as assigned
     to a missing Node and deletes it.

  5. Work agent reconciles: desired Pod still in ManifestWork, live Pod
     gone → recreate.

  6. Loop continues (may be seconds to minutes between flaps depending
     on controller timing — not necessarily a tight busy-loop).

  7. ManifestWork typically stays Applied=True with Available=False
     while the Pod is missing / not ready.

    Edge Pod hardcoded-node-pod appears and disappears at least once

    WDS Pod stays Present the whole time
    ManifestWork for the Pod shows Applied=True and typically

Clean slate (re-run)
--------------------
  export KUBECONFIG=~/.kube/kubeflex

  kubectl --context wds1 delete bindingpolicy ursa-bp-hardcoded-node-pod-repro --ignore-not-found

  for ctx in edge-1 edge-2; do
    kubectl --context $ctx delete pod hardcoded-node-pod --ignore-not-found --wait=false --force --grace-period=0 2>/dev/null || true
    kubectl --context $ctx delete configmap ursa-configmap-template --ignore-not-found
  done

  kubectl --context wds1 delete pod hardcoded-node-pod --ignore-not-found --wait=false
  kubectl --context wds1 delete configmap ursa-configmap-template --ignore-not-found

  sleep 30



Expected behaviour
------------------
  1. If an edge system controller deletes a downsynced object for a local
     reason (orphan node, policy, etc.), the hub/work-agent should not
     blindly recreate it forever.

  2. Prefer: surface the deletion / unavailability in ManifestWork /
     status, back off recreates, and/or reflect failure to the user on
     the hub — rather than an unbounded create/delete loop.
