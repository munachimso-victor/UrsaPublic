Manual repro: PVC volumeName null / empty-string → immutable fight → hub stops tracking
========================================================================================

Self-contained bug submission bundle. All paths below are relative to this folder:

  manual_tests/pvc_volumename_repro/


Goal
----
Reproduce the PVC apply failure where:

  - WDS PVC is created with volumeName: null OR volumeName: ""
  - BindingPolicy downsyncs PVC (+ prebound PV via claimRef) to the edge
  - Edge PVC binds; controller fills volumeName = ursa-csipv-template
  - Work agent re-applies WDS desired state (volumeName null / "")
  - Klusterlet apply fails: Forbidden: spec is immutable after creation
  - ManifestWork status shows AppliedManifestWorkFailed with a diff like:
      - "VolumeName": "ursa-csipv-template",
      + "VolumeName": "",
  - After that failure, the hub stops tracking the PVC (labels no longer
    downsync). Other objects in the same BindingPolicy (e.g. StorageClass)
    can still update.

Ursa automated hits (same mechanism):
  tests/2026-07-26_shard5/run_ursa-bp-pvc__pert__reset_always/ursa-csipv-template/
    testcase_001_ursa-bp-pvc_null_ursa-csipv-template.txt
    testcase_003_ursa-bp-pvc_empty_string_ursa-csipv-template.txt


How tracking ends on the PVC (step-by-step)
-------------------------------------------
  1. Desired state on WDS
     Apply seed with PVC.spec.volumeName: null  (scenario A)
     or PVC.spec.volumeName: ""               (scenario B).
     PV has claimRef → this PVC (static / prebind pattern).
     storageClassName is set to ursa-storageclass-template on both
     (so this is NOT the storageClassName=null bug).

  2. BindingPolicy selects edge-1 / edge-2 and downsyncs
     Namespace, StorageClass, PersistentVolume, PersistentVolumeClaim.

  3. KubeStellar creates ManifestWorks on ITS (ns=edge-*).
     Work agent on the spoke applies the wrapped manifests.

  4. Spoke PVC is created, then the PV binder fills
     PVC.spec.volumeName = "ursa-csipv-template" (immutable once bound).
     Edge live object now differs from WDS desired (null / "").

  5. Work agent keeps trying to apply WDS desired onto the spoke.
     API server rejects the volumeName change:
       Forbidden: spec is immutable after creation
       except resources.requests and volumeAttributesClassName for bound claims

  6. ManifestWork condition Applied=False (AppliedManifestWorkFailed).
     resourceStatus shows the VolumeName diff (edge has the PV name;
     desired is empty string — null often serializes the same way).

  7. Hub stops tracking that PVC for further updates:
     patching a label on WDS PVC does not appear on the edge PVC;
     edge PVC resourceVersion stays put. Sibling objects (StorageClass)
     in the same policy still track — failure is per ManifestWork /
     per object, not a total BindingPolicy death.

Step 3 — Reproduce
------------------
  export KUBECONFIG=~/.kube/kubeflex
  cd /path/to/manual_tests/pvc_volumename_repro

  # Clean slate between scenarios (see bottom of this file).

  # --- Scenario A: volumeName: null ---
  kubectl --context wds1 apply -f pvc_volumeName_null.yaml
  kubectl --context wds1 apply -f pvc_policy.yaml

  # --- Scenario B: volumeName: "" (empty string) ---

  sleep 60


Step 4 — Verify the apply failure
---------------------------------
  kubectl --context its1 -n edge-1 get manifestworks

  kubectl --context its1 -n edge-1 get manifestworks -o yaml | \
    grep -B5 -A80 'kind: PersistentVolumeClaim'

  SUCCESS CRITERIA:
    Applied=False, reason=AppliedManifestWorkFailed
    message contains:
      Forbidden: spec is immutable after creation
      - "VolumeName": "ursa-csipv-template",
      + "VolumeName": "",

  NOTE: WDS may store volumeName: null while the status diff shows "" —
  both scenarios collide with the bound edge value the same way.


Step 5 — Verify hub stops tracking the PVC
------------------------------------------
  export KUBECONFIG=~/.kube/kubeflex

  # --- 5a. StorageClass (healthy downsync; label should still propagate) ---

  kubectl --context edge-1 get storageclass ursa-storageclass-template \
    -o jsonpath='edge SC resourceVersion={.metadata.resourceVersion}{"\n"}'
  kubectl --context edge-1 get storageclass ursa-storageclass-template --show-labels

  kubectl --context wds1 label storageclass ursa-storageclass-template \
    repro-sc-after-failure=updated --overwrite

  sleep 60

  kubectl --context wds1 get storageclass ursa-storageclass-template --show-labels
  kubectl --context edge-1 get storageclass ursa-storageclass-template --show-labels
  kubectl --context edge-1 get storageclass ursa-storageclass-template \
    -o jsonpath='edge SC resourceVersion={.metadata.resourceVersion}{"\n"}'

  # --- 5b. PVC (failed ManifestWork; hub stops tracking) ---

  kubectl --context edge-1 get pvc -n ursa-namespace-template ursa-pvc-template \
    -o jsonpath='edge PVC resourceVersion={.metadata.resourceVersion}{"\n"}'
  kubectl --context edge-1 get pvc -n ursa-namespace-template ursa-pvc-template --show-labels

  kubectl --context wds1 label pvc ursa-pvc-template -n ursa-namespace-template \
    repro-pvc-after-failure=updated --overwrite

  sleep 60

  kubectl --context wds1 get pvc -n ursa-namespace-template ursa-pvc-template --show-labels
  kubectl --context edge-1 get pvc -n ursa-namespace-template ursa-pvc-template --show-labels
  kubectl --context edge-1 get pvc -n ursa-namespace-template ursa-pvc-template \
    -o jsonpath='edge PVC resourceVersion={.metadata.resourceVersion}{"\n"}'

  SUCCESS CRITERIA (5a — StorageClass):
    WDS StorageClass has label repro-sc-after-failure=updated
    Edge StorageClass also has repro-sc-after-failure=updated

  SUCCESS CRITERIA (5b — PVC):
    WDS PVC has label repro-pvc-after-failure=updated
    Edge PVC does NOT have repro-pvc-after-failure=updated
    Edge PVC resourceVersion unchanged after the WDS label patch
    ManifestWork PVC entry still Applied=False

What NOT to do
--------------
  - Run kubectl without KUBECONFIG=~/.kube/kubeflex
  - Apply manifests from the Ursa repo root (use this folder)
  - Apply fix-klusterlet-rbac.yaml on WDS instead of edges
  - Use clusteradm v1.x with KubeStellar 0.29 hub
  - Confuse this with pvc_null_storageclass_repro (that one uses
    storageClassName: null; this one keeps storageClassName set)


Expected behaviour
------------------
  1. Hub and edge should not fight over a field the spoke binder filled in
     (volumeName after bind). Desired state on WDS should either omit an
     immutable late-bound field or learn the effective edge value.

  2. Partial tracking after an apply failure would be preferable: keep
     downsyncing mutable fields (labels, annotations) even when volumeName
     cannot be reconciled. Losing all tracking for one immutable field
     leaves the spoke object unmanaged.
